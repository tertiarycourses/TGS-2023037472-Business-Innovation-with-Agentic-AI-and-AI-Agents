## 1.1 A Short History of AI

| Approach | Wider adoption (illustrative) | What changed |
|---|---|---|
| Rules | 1950s-1980s | People write explicit if-then rules and expert systems. |
| Machine Learning | 1990s-2000s | Algorithms learn patterns from training examples for predictions or classifications. |
| Deep Learning | 2010s | Multi-layer neural networks learn useful features; ImageNet (2012) is a landmark. |
| LLM | 2020s | Large language models learn language patterns at scale; GPT-3 (2020) is a landmark. |

This is a teaching progression of wider adoption, not a claim about invention dates. Machine learning and neural networks began earlier. Deep learning is a form of machine learning, and modern LLMs use deep neural networks. The approaches coexist: an agent may still use business rules, conventional software and databases.

*Source: Krizhevsky et al., ImageNet Classification with Deep Convolutional Neural Networks (2012), proceedings.neurips.cc; Brown et al., Language Models are Few-Shot Learners (2020), https://arxiv.org/abs/2005.14165 ; IBM, History of Artificial Intelligence (checked 18 Nov 2026).*

### 2023 to 2026: four engineering lenses

A teaching sequence of where practitioners focused their effort. The years are emphasis markers, not invention dates; each lens overlaps the others and each adds an architecture implication.

| Lens | Emphasis | Architecture implication |
|---|---|---|
| Prompt engineering | 2023 | Specify goal, audience, format and examples; version prompts like code. |
| Context engineering | 2024 | Retrieve the right facts at the right time (RAG, memory); control what enters the context window. |
| Harness engineering | 2025 | Wire tools, state, permissions, checks and logs around the model so it can act safely. |
| AI agents | 2026 | Delegate outcomes; design human decision boundaries, evaluation and monitoring for autonomous work. |

## 1.2 Always-On AI Agents: A Specialised Form of Agentic AI

|  | Agentic AI | Always-on AI agent |
|---|---|---|
| What it is | The broad class of goal-directed AI that plans, uses tools and checks results | A specialised persistent implementation of those capabilities |
| When it runs | May be started for one task or deployed as a continuing service | Keeps monitoring between user messages through event or schedule triggers |
| How it behaves | Plans, acts, checks and repeats within defined limits | Maintains state, watches for work, performs permitted tasks and escalates for approval |

This course focuses on the ALWAYS ON class: agents deployed to keep watching and working between your requests. More generally, an AI agent is a concrete software worker built with agentic capabilities; it can also be invoked for a single task. Persistence is a deployment choice, rather than a defining requirement of every AI agent. Examples here include an inbox watcher or an agent that checks deadlines on a schedule, within the permissions you give it.

*Source: Anthropic, Building effective agents: https://www.anthropic.com/research/building-effective-agents (checked 18 November 2026).*

### How an AI Agent Works

Give an agent a goal and boundaries. It uses relevant context and memory, selects a permitted tool, checks the result and decides the next step or escalates. For a service request it can extract the site and fault, draft a ticket and check required fields; a coordinator approves urgent routing. Autonomy depends on granted permissions and controls.

| Component | What it does | Example in Claude Code |
|---|---|---|

### AI Agents as the Interface to Software and SaaS

Instead of navigating many software screens, a person describes a task to an AI agent. The agent selects configured tools, sends permitted requests to the relevant software and reports the result. An API exposes application functions; MCP standardises how tools are described and called, often with a server that wraps an existing API. MCP does not bypass authentication or the software's permissions.

| Example request | What the agent does | Business benefit |
|---|---|---|
| Sales: Find overdue follow-ups and create CRM tasks for account owners. | Read permitted CRM records, identify overdue follow-ups, create assigned tasks and report the task IDs. | Less screen navigation; new staff can work through a familiar task description. |
| HR: Check my leave balance and prepare a request for next Friday. | Read the authorised employee balance, check the policy and prepare a leave request for the manager. | Faster routine HR self-service; the manager retains the approval decision. |
| Finance: List overdue invoices and draft reminders for my approval. | Retrieve invoice status from the accounting system, prepare a review list and draft messages without sending. | Less manual searching and re-keying; finance staff review exceptions and approve sends. |

These are illustrative configured workflows, not integrations supplied automatically by every agent. Faster onboarding is a benefit to test: staff still need the company's rules, judgement and approval responsibilities. Another example is a meeting assistant that checks calendars and proposes an appointment through a calendar API; inviting others needs the user's approval.

*Source: MCP tools specification: https://modelcontextprotocol.io/specification/2025-06-18/server/tools ; Microsoft Graph calendar API: https://learn.microsoft.com/en-us/graph/api/user-post-events?view=graph-rest-1.0 (checked 18 November 2026).*

### A Service Agent: Knowledge, Live Data and Action

An online-store customer asks: 'Where is my order, and can I change the delivery address?' A knowledge-only chatbot might explain the delivery policy. A configured service agent can complete a longer workflow:

1. Search the approved knowledge base for the current delivery and address-change rules; explain the relevant rule.
2. Verify the customer and use an authorised order-system tool to check this order's dispatch status.
3. If the policy and permissions allow a change, confirm the new address, update it and provide a confirmation. If the parcel has already dispatched or the case is unusual, create a support ticket and hand over to a person.

Business benefits include after-hours service, repetitive work without human fatigue and a consistent approved workflow. Additional agent instances can run the same workflow for more customers in parallel. Each customer's session and permissions must stay separate, while the instances use common live order state and duplicate-action checks. Scaling is not unlimited: hosting, API quotas, costs, monitoring and human exception-handling capacity still matter.

### Multi-Agent Video Production Team

A human producer briefs the team: 'Create a 30-second product-launch video for this audience, using this offer, brand guide and budget.' Specialist agents share one approved brief and a common asset folder:

1. The script agent drafts the story, script and shot list. The human producer approves the script and spending cap before production.
2. Visual and voice/music agents work in parallel on the approved shots, narration and soundtrack. They keep versioned files in the shared project folder.
3. The editing agent assembles clips, captions and audio using connected production tools.
4. A separate review agent checks facts, brand consistency, captions, continuity and the media-rights checklist. It flags issues for correction; its review does not replace human judgement.
5. The human producer reviews the final video and approves release before anything is published.

This team can reduce hand-off time and run asset work in parallel. Reuse approved instructions for the next campaign or add agent instances for more projects, while keeping each project's assets, permissions and budget separate. Measure turnaround, revision time, cost and quality. API/MCP automation depends on the production platforms exposing the necessary actions; a human can perform an unsupported step.

### Multi-Agent Trading Team: A Research-to-Review Loop

An illustrative trading team can assign several agents to each of five roles, coordinated by one accountable human strategy owner. In training, use paper trading:

1. Data agents gather financial statements, market prices and news from authorised sources. They check quality and preserve timestamps so research does not use future information.
2. Research agents propose algorithms or hypotheses, backtest them on historical data and generate signals. Evaluate held-out data and realistic transaction costs.
3. Execution agents apply the approved risk checks, route simulated orders through a paper-broker API, and record orders and fills. Shared order state and unique order IDs help prevent duplicate or conflicting trades.
4. Analysis agents reconcile profit/loss and measure drawdown, costs, slippage, signal quality and execution performance.
5. Review agents investigate outcomes and drift, then propose a new algorithm version. Feed it back to research and testing; the human owner approves the version before live deployment.

The human owner sets capital and position limits, pause conditions and approval responsibilities. Multiple agents can explore ideas and analyse evidence in parallel, but an attractive backtest or simulation is not proof of live profitability. The example describes an operating model; it does not execute real trades.

*Source: Alpaca, Paper Trading: https://docs.alpaca.markets/us/docs/paper-trading (checked 18 November 2026).*

### Scientific Agent Team: A Literature-to-Evidence Loop

Start with one research question and one accountable human researcher. Teams of specialist agents share a versioned research notebook:

1. Literature agents search relevant papers, record citations, map existing evidence and identify gaps.
2. Theory agents propose competing explanations, falsifiable hypotheses and measurable predictions.
3. Experiment-design agents propose controls, measurements, resource needs and an analysis plan. The researcher approves the protocol before testing.
4. Testing agents run approved simulations or coordinate authorised experiments with laboratory staff or connected instruments; they capture observations and provenance.
5. Analysis agents compare observations with predictions, assess uncertainty and check reproducibility. Supporting and contrary evidence both return to the theory and literature teams, which revise or reject hypotheses and design the next experiment.

The human researcher defines the question, approves protocols and resources, checks the validity of the evidence and decides what claims the findings support. This is an illustrative team design: an agent's proposed experiment or explanation is not experimental evidence by itself.

## 1.7 What the Business Model Canvas Shows

The Business Model Canvas (BMC) maps how a company creates, delivers and captures value across nine connected blocks. Start with who is served and why they choose you; link channels and relationships to the activities, resources and partners needed; then check revenue and costs. AI agents may improve several blocks, but the whole model must still make sense.

| BMC block | Meaning | Meridian agent use and benefit |
|---|---|---|
| Customer Segments | Who the business serves | Building managers need fast status updates; premium clients keep a named human. A routine service agent frees account managers for complex client needs. |
| Value Propositions | Why customers choose it | Triage drafts tickets and tracks requests around the clock. Faster acknowledgement and clearer job status; urgent faults still escalate to people. |
| Channels | How the business reaches customers | Agents draft email and WhatsApp replies and prepare portal updates. More consistent updates across channels; coordinators approve sends during the pilot. |
| Customer Relationships | How customers are supported and retained | Routine status queries go to the agent; complaints and refunds go to coordinators. Responsive service with a reachable human; the service-desk head owns quality. |
| Revenue Streams | How the business earns money | Test a premium two-hour response tier; faster updates may protect renewals. A possible SGD 6,000/month uplift is an assumption to validate, not booked revenue. |
| Key Activities | What the business must do well | Agents draft triage tickets, propose schedules and compile client reports. Less re-keying and reporting work; supervisors retain dispatch decisions. |
| Key Resources | The assets and know-how it needs | Use permitted tickets, technician notes and coordinator routing knowledge. Make operational knowledge reusable; clean and mask data before access. |
| Key Partners | The external parties it relies on | Ticketing vendor, agent platform and building owners agree data/API access. Connect the service workflow with clear access rights and partner responsibilities. |
| Cost Structure | What running the business costs | Budget SGD 39,000 in year one for licences, integration, training and change. Test whether time saved exceeds full costs; include human review and assurance. |

Read these proposed benefits as hypotheses. Faster replies do not guarantee retention or new revenue. The predictor is a future option, parked until its data is ready; the premium response tier also needs validation. Human approval remains on urgent jobs, complaints and refunds.

## 1.8 Why AI Projects Stall: Five Capability Gaps

Deploy a model straight out of the box and five structural gaps appear at once:

1. Private data: contracts, customer records and internal processes are blank to it.
2. Internal language: 'active customer' or 'closed' may mean something different in your company.
3. Live context: it does not know what changed a second ago.
4. Ability to act: it has no permission to execute inside your systems.
5. Guardrails: no permission controls, verification of results or audit trail.

Like a brilliant graduate nobody onboards, the model stays stuck on day one. A business opportunity is viable only if you can close these gaps for it.

## 1.9 Investigating and Evaluating Opportunities (A1, A2)

Analyse the business need before you pick technology. Gather evidence from five sources:

| Evidence | Questions | Example (a service desk) |
|---|---|---|
| Stakeholders | Who feels the pain? What does each want and fear? | Clients chase job status; coordinators fear replacement. |
| Process | Trigger, steps, hand-offs, waits, rework, decisions? | 6 steps, 3 hand-offs, 38% of time re-keying. |
| Data | What data exists, is it clean, current and permitted? | 5 years of tickets; tenant phone numbers must be masked (PDPA). |
| Requirements | What must the solution do, testably, and who signs it off? | Draft a ticket within 1 minute; coordinator approves urgent jobs. |
| Opportunity | Which objective does it move, by how much, at what cost and risk? | Handling time 18 to 11 minutes; same-day response objective. |

Score each idea on value, feasibility and data readiness (1-5 each) and check it serves an organisational objective. Set a veto: a score of 1 on data or risk stops the idea whatever the total. Four value levers: revenue, cost, risk and experience.

## Step 2 · Mine the Business Process

### Dormant Data Is a Gold Mine

A company keeps two sets of records. The official set (reports, reviews, strategy papers) is polished and filtered. The second set records what actually happened: meeting audio, chat logs, edit history, customer tickets, code logs, photos and system logs. It is often fragmented, incomplete or biased, and until now too hard to analyse at scale. This is dormant data. Multimodal AI can help analyse text, audio, images, spreadsheets and logs together, so this record becomes usable.

*[Figure: Awakening dormant data]*

Dormant data is a potential gold mine because it contains clues to recurring faults, customer needs and process delays. Value comes from a verified business decision, rather than the volume of data collected. Check permission, quality, freshness and coverage before use, then trace each finding to its source and compare the result with a baseline.

| Source | Opportunity | Measure |
|---|---|---|
| Meridian's closed tickets and technician notes | Find repeat faults and missing information | Repeat visits and rework rate |
| Customer chats and complaints | Find repeated questions and renewal concerns | Resolution time and retention |
| Quotation and approval timestamps | Locate waiting and avoidable handoffs | Lead time and conversion |

### Map the Current Workflow

1. Pick one process that hurts every week.
2. Pull its trail from dormant data: emails, tickets, logs, chats, meeting notes.

### Process Mining with Meridian's Ticket Events

Process mining reconstructs observed workflows from event logs. Start with one row per event and include case ID, activity and timestamp. For example, M-101 has separate rows for Request (09:00), Draft (09:04), Approval (09:10) and Dispatch (09:12). Group by case ID, sort by timestamp and compare the resulting paths. Discovery shows common paths and variants. Conformance checks their order against the approved process. Performance analysis measures elapsed times and helps locate delays and rework.

| Case ID | Events in timestamp order | Time to dispatch |
|---|---|---|
| M-101 | 09:00 Request → 09:04 Draft → 09:10 Approval → 09:12 Dispatch | 12 min |
| M-102 | 09:00 Request → 09:04 Draft → 09:08 Returned for details → 09:45 Redraft → 09:50 Approval → 09:53 Dispatch | 53 min |
| M-103 | 09:00 Request → 09:04 Draft → 09:08 Dispatch | 8 min |

Meridian's SOP requires approval before dispatch. M-102 returns for missing details and takes 50 minutes from request to approval. This measures elapsed time, including work and waiting. M-103 has no approval event in the sample. Check the approval source and log completeness with the process owner before concluding the rule was breached.

### The Enterprise AI Decision Layer

Four connected components turn data into intelligence across the whole company:

| Component | Role | Why it matters |
|---|---|---|
| Brain: the model | Reasons, infers and judges | Commoditising fast; a better model alone moves performance from D to D+. |
| Map: the ontology | Defines business terms, entities, relationships and rules | Lets AI anchor every action in your business context; your moat. |
| Navigation: live context | Tracks every event in real time | The map shows what should happen; navigation shows what is happening. |
| Operating system | Scheduling, execution, access, control | Lets agents act within authorised, recorded and stoppable boundaries. |

*[Figure: The four core components of enterprise AI decision-making]*

### The operating system's four subsystems

- Scheduling: plans the order of work, divides it among agents and knows how to wait days for an approval, then resume.
- Execution: tests each action in a sandbox first, then runs an execute-check-correct loop.
- Access: a universal keycard to CRM, ERP, email and documents; the Model Context Protocol (MCP) lowers the cost of each connection.
- Control: grant a task-specific identity only the required permissions, enforce approval gates in connected systems and log actions.

### Drawing the Company Map

An ontology, or company map, is a semantic structure that defines key business terms (what a customer, contract or approval is) and how they relate. It covers people, customers, products, orders, contracts, approval flows and business rules. Without it a model cannot see why active customers are tied to payment terms, or why three more approvals follow a signed contract. Build it in layers: data sources, data models, business rules, relationships. Today it can be drawn and revised in plain language by the people who run the business (ontology 2.0), instead of taking 6-18 months of specialist work.

| Briefing component | What to provide | Meridian example |
|---|---|---|
| Business purpose | Products, customers, service promises and success measures | Meridian: draft accurate triage tickets; target 18 to 11 minutes per request. |
| Operations and process | Trigger, steps, roles, handoffs, systems, inputs and outputs | Request arrives → classify → draft ticket → coordinator approves → dispatch → close. |
| Company language and data | Entity definitions, relationships, permitted records and live status | Link each building to its contract, assets, service level and responsible coordinator. |
| Policies and authority | Approved SOPs, versions, thresholds, exclusions and escalation owner | Urgent leak: alert the duty coordinator; no autonomous dispatch, refunds or external sends. |
| Examples and validation | Good cases, exceptions, expected outcomes and a named reviewer | Test routine, urgent, incomplete and conflicting requests; owner signs off before the pilot. |

Meridian pilot example: the agent may read permitted request and contract records, classify requests and draft tickets. An urgent leak triggers an alert to the duty coordinator. 1. Brief: give the task, process, definitions and current policy sources.

## S · Story: Communicate the Change

Explain why Meridian is piloting triage, what the agent will draft, what staff still decide and when the plan will be reviewed. Explain the no-job-loss commitment for the pilot. Use a team huddle for coordinators, a service update for customers and a short review for leaders. Give each group a named contact for questions.

## C · Commanders: Give the Rollout an Owner

*[Figure: Rewrite companies in a flattened org chart]*

A Directly Responsible Individual (DRI), a term from Apple, is the one person accountable for an outcome: singular (one named person, not a committee), accountable (owns the outcome, not just the task) and holding the decision rights (commands the AI workforce). DRIs carry responsibility to the end, are self-driven, coordinate without formal authority and now command agents. Agents supply capability; the DRI supplies accountability.

### Flatten smart, not by decree

Block laid off about 4,000 people (nearly 40%) at once; about 30% of Zappos staff left after the Holacracy ultimatum in 2015; Google removed engineering managers in 2001 and reinstated them within months. Flattening by decree wipes institutional memory. The right order: preserve and codify the knowledge in the decision layer first, then simplify the hierarchy. Bayer cut from 12-13 layers to 6-7 over a planned three-year journey.

1. Codify tacit know-how into the company map and skills.
2. Run a business scenario test: real access to agents, a small valuable task, four boundaries (goal, time, data, token spend).
3. Spot the builders; they are your first DRIs.
4. Give each DRI matching decision rights and resource rights.
5. Let relay layers fade as more DRIs emerge.

| Type seen in the test | What to do |
|---|---|
| Learners: use AI as a better search | Give time and coaching |
| Followers: forward unchecked 'workslop' | Do not mistake it for productivity |
| Irreplaceable experts | Pair with tool users; extract their knowledge |
| Builders: become a small team at once | Your first DRIs; give them authority to match |

### Progressive Implementation

Start with shadow mode, where the agent drafts alongside normal work. Move to assist mode with a person approving each action. Test supervised autonomy only for low-risk tasks that pass the agreed checks. Meridian starts with two sites, expands to ten after review and keeps human approval for dispatch. The DRI pauses the rollout when quality or safety falls outside limits.

## A · Augment People: Redesign Roles and Coach

| Role | Outlook |
|---|---|
| Amplified commander (DRI) | Manages many agents, raises output tenfold; most valuable |
| Human-to-human work | Trust, warmth, negotiation, calming a customer; endures |
| Rubber-stamp manager | Signs off AI output without judging; hollowed out |
| Rule-bound, predictable work | AI already does it better, faster, cheaper; reskill |

Managers move from relaying information to judgement: the judge at scale who owns outcomes for agents and people; the coach who teaches teams to work with agents; the translator and connector who moves tacit knowledge into the system during transition. The manager who only holds meetings and passes on approvals is most exposed.

## 3.3 The Learner's Advantage and the Atrophy Trap

Stanford and MIT researchers tracking more than 5,000 customer-service agents found AI help raised issues resolved per hour by over 10%, and by over 30% for new and weaker staff; a two-month hire performed like a six-month one. The difference that matters now is appetite for mental effort. But judgement decays with disuse: doctors' detection of precancerous lesions fell from 28.4% to 22.4% after the AI tool was removed, and people accepted planted wrong AI answers 80% of the time (Wharton). Ask for hints before answers, write your position first, and keep some work unassisted.

### Redesign the Job Around a Human Owner

Choose a named person to own each outcome. Give that person authority to set direction, approve consequential actions, resolve exceptions, pause the workflow and update the operating rules. Define the agent’s delegated work and record what the human checks. Judge the redesigned role by outcomes such as accurate tickets, response times and safe decisions.

| Human responsibility | What the owner does |
|---|---|
| Direct | Set the goal and limits on data, tools and actions. |
| Challenge | Check evidence and test assumptions. |
| Decide | Approve consequential actions and release decisions. |
| Escalate | Handle exceptions, pause work and own recovery. |
| Improve | Update instructions, tools and rules based on results. |

Meridian’s Head of Service Desk sets service targets and authorises the workflows. The agent extracts request details, drafts tickets and flags urgency. Coordinators check the evidence and approve dispatch. The Head of Service Desk reviews exceptions and can pause the workflow or change the rules.

A second example is Sarah, a marketing lead. The agent drafts campaign copy and decks. Sarah owns campaign outcomes, sets the creative direction, checks factual claims and approves release. She and her manager agree a two-week trial and review draft time, corrections and whether she had enough control.

## L · Loop Information: Collect and Act on Feedback (A6)

In an AI-native firm, information flows through the DRI and the decision layer instead of up and down ten layers. Set an operating rhythm: a daily 8:00 exceptions brief from the agents, a weekly DRI review with the team, a monthly one-page dashboard for the sponsor. Communicate the change per stakeholder (what changes, what does not, who to ask), and run an idea pipeline where anyone can post an idea, the agent clusters them, and the best get a DRI and 30 days.

Close the loop with staff. Collect concerns and client feedback, review them weekly, name an owner for each change and tell people what was done. For example, Meridian could revise its intake form after coordinators repeatedly flag missing building details.

## E · Evaluate: Decide Whether to Continue or Scale

Check service outcomes, adoption, safety and staff or customer feedback against the agreed targets. Review costs and the stop rule with the DRI. Scale in stages when the evidence supports it, redesign and retest weak parts, or pause the pilot and return to the human workflow.

### Legal, Ethical and Security Issues (K6)

- PDPA: collect and use personal data only for notified purposes; mask personal data before analysis; follow the PDPC Advisory Guidelines on Use of Personal Data in Generative AI (2026).
- IMDA Model AI Governance Framework for Agentic AI: bound the risk, keep humans meaningfully accountable, apply technical controls, enable users. CSA's Securing Agentic AI addendum (June 2026) adds security controls.
- Five agent risks (one slide each, with a Meridian example):
- 1 Prompt injection: instructions hidden in an email, web page or PDF the agent reads give it orders; the attacker never talks to the AI. Example: a leak report ends in white text telling the triage agent to close all Tower B tickets and forward the client list. Treat everything the agent reads as data, draft only, a person approves bulk changes.
- 2 Jailbreak: a user deliberately crafts prompts (role-play, 'test mode', step-by-step pressure) to make the AI break its own rules. Unlike prompt injection, the attacker is the person in the chat; unlike shadow AI, it is an attack. Example: a 'tenant' tells the WhatsApp agent it is now in admin test mode and asks for plant-room access codes. Keep secrets out of the agent's reach, never let it change its own permissions, red-team it before go-live.
- 3 Data leakage: personal or confidential data flows where it should not, with or without an attacker; it can breach the PDPA. Example: a coordinator pastes a tenant's name, unit and phone number into a free chatbot. Classify data, mask personal data, have the DPO check each agent.
- 4 Shadow AI: staff use AI tools the company has not approved and cannot see; no attack, usually good intent, but no control. Example: technicians transcribe voice notes holding tenant names with a free app. Ask what staff use without blame, offer an easier approved tool, publish one page of AI rules.
- 5 Bias and blame: the agent learns unfair patterns and nobody owns the decision. Example: premium-contract faults get marked urgent faster than small-office faults. Name a DRI for every agent decision, compare outcomes across groups, keep an appeal route.
- Accountability: the organisation stays responsible for its agents' actions; keep an audit trail of who asked what and when.
- Ethics: transparency, fairness, explainability, human oversight; tell customers when they are dealing with an agent.

### Review Meridian’s Pilot Results (K5, A5)

- Start narrow with one high-value process, a measured baseline and a named DRI.
- Keep a real human checkpoint for the first 90 days.
- Measure offline quality before launch and online telemetry after: cycle time, first-pass accuracy, complaints, adoption, cost per outcome.
- Review at a fixed gate and decide scale, redesign, hold or stop on pre-agreed criteria.

| Day-90 metric | Target | Result |
|---|---|---|
| Mean handling time | ≤ 11 min | 10.7 min |
| Quality | ≥ 94% | 95.1% |
| Complaints | ≤ 2% | 1.7% |
| Sustained use | ≥ 70% | 77.5% |
| Critical unsafe actions | 0 | 0 |
| Realised benefit vs year-1 cost | benefit ≥ cost | SGD 39,200 vs SGD 39,000 |

ROI = (realised benefit - cost) / cost. Here year-1 ROI is close to zero but recurring costs are lower, so the case for scaling rests on year 2 and on keeping quality. Always add a downside case (lower adoption, smaller time saving).
